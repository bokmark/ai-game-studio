# 代理协调规则

1. **垂直委派**:领导层代理委派给部门主管,部门主管再委派给
   专家代理。复杂决策不得跨级。
2. **横向协商**:同层级代理之间可以互相协商,
   但不得在自己的领域之外做出有约束力的决策。
3. **冲突解决**:两名代理意见不合时,升级给共同的
   上级。若无共同上级,设计冲突升级给 `creative-director`,
   技术冲突升级给 `technical-director`。
4. **变更传播**:当某项设计变更影响多个领域时,由
   `producer` 代理协调传播。
5. **禁止单方面跨领域变更**:代理绝不应在没有明确委派的
   情况下修改其指定目录之外的文件。

## 模型层级分配

技能与代理按任务复杂度分配到不同模型层级:

| 层级 | 模型 | 何时使用 |
|------|-------|-------------|
| **Haiku** | `claude-haiku-4-5-20251001` | 只读状态检查、格式化、简单查询——无需创造性判断 |
| **Sonnet** | `claude-sonnet-4-6` | 实现、设计文档撰写、单系统分析——大多数工作的默认值 |
| **Opus** | `claude-opus-4-6` | 多文档综合、高风险阶段门裁决、跨系统整体评审 |

使用 `model: haiku` 的技能:`/help`、`/sprint-status`、`/story-readiness`、`/scope-check`、
`/project-stage-detect`、`/changelog`、`/patch-notes`、`/onboard`

使用 `model: opus` 的技能:`/review-all-gdds`、`/architecture-review`、`/gate-check`

其余技能默认使用 Sonnet。创建新技能时:若技能只读取和格式化,
分配 Haiku;若必须综合 5 份以上文档且产出高风险结论,分配 Opus;
否则不设置(即 Sonnet)。

## 子代理与代理团队

本项目使用两种不同的多代理模式:

### 子代理(当前方案,始终启用)
在单个 Claude Code 会话内通过 `Task` 派生。所有 `team-*` 技能
和编排技能都使用它。子代理共享会话的权限上下文,在会话内
串行或并行运行,并将结果返回给父级。

**何时并行派生**:若两个子代理的输入相互独立(双方都不需要
对方的输出才能开始),则同时发起两个 Task 调用,而不是排队
等待。示例:`/review-all-gdds` 的第 1 阶段(一致性)与第 2 阶段
(设计理论)相互独立——同时派生。

### 代理团队(实验性——需显式启用)
多个独立的 Claude Code *会话*同时运行,通过共享任务
清单协调。每个会话有自己的上下文窗口和 token 预算。
需要 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 环境变量。

**适用代理团队的情形**:
- 工作横跨多个不会改动相同文件的子系统
- 每条工作流耗时超过 30 分钟,能从真正的并行中获益
- 某资深代理(technical-director、producer)需要协调 3 个以上
  同时处理不同 Epic 的专家会话

**不适用代理团队的情形**:
- 某会话的输出是另一会话的输入(改用串行子代理)
- 任务在单个会话上下文内即可完成(改用子代理)
- 成本敏感——每位团队成员独立消耗 token

**当前状态**:通过 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 显式启用。首次采用时请在此记录使用情况。

## 并行任务协议

当编排技能派生多个相互独立的代理时:

1. 先发出所有独立的 Task 调用,再等待任何结果
2. 收齐所有结果后,再进入有依赖关系的后续阶段
3. 若有代理受阻(BLOCKED),立即显式上报——不得静默跳过
4. 若部分代理完成、部分受阻,始终产出部分报告
