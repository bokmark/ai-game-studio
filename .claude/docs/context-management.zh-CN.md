# 上下文管理

上下文是 Claude Code 会话中最关键的资源。请主动管理它。

## 文件化状态(首要策略)

**文件才是记忆,对话不是。** 对话是短暂的,
会被压缩或丢失。磁盘上的文件能在上下文压缩和会话崩溃后存续。

### 会话状态文件

维护 `production/session-state/active.md` 作为动态检查点。每达成一个重要
里程碑后更新它:

- 设计小节获批并写入文件
- 做出架构决策
- 达成实现里程碑
- 获得测试结果

状态文件应包含:当前任务、进度清单、已做出的关键决策、
正在处理的文件,以及待解决的问题。

### 状态栏信息块(仅限 Production 及之后阶段)

当项目处于 Production、Polish 或 Release 阶段时,在 `active.md` 中
包含一个结构化的状态块,供状态栏脚本解析:

```markdown
<!-- STATUS -->
Epic: Combat System
Feature: Melee Combat
Task: Implement hitbox detection
<!-- /STATUS -->
```

- 三个字段(Epic、Feature、Task)均为可选——只填适用的
- 切换工作重点时更新此块
- 状态栏会将其显示为面包屑:`Combat System > Melee Combat > Hitboxes`
- 当前无活跃工作重点时,移除或清空此块

发生任何中断(压缩、崩溃、`/clear`)后,先读取状态文件。

### 增量式文件写作

创建多小节文档(设计文档、架构文档、设定条目)时:

1. 立即创建文件骨架(所有小节标题齐全,正文留空)
2. 在对话中逐节讨论并起草
3. 每节获批后立即写入文件
4. 每写完一节更新会话状态文件
5. 某节写入文件后,此前关于该节的讨论即可安全压缩——
   决策已在文件中

这让上下文窗口只需容纳*当前*小节的讨论
(约 3-5k token),而不是整个文档的对话历史(约 30-50k token)。

## 主动压缩

- **主动压缩**:在上下文用量约 60-70% 时进行,而不是等到触顶才被动处理
- **使用 `/clear`**:在互不相关的任务之间,或连续 2 次以上纠正失败之后
- **天然压缩点:** 某节写入文件后、提交后、
  完成一项任务后、开始新话题前
- **聚焦压缩:** `/compact Focus on [current task] — sections 1-3 are
  written to file, working on section 4`

## 按任务类型划分的上下文预算

- 轻量(阅读/评审):启动约 3k token
- 中等(实现功能):约 8k token
- 重度(多系统重构):约 15k token

## 子代理委派

使用子代理做调研和探索,保持主会话整洁。
子代理在各自的上下文窗口中运行,只返回摘要:

- **使用子代理**:需要跨多文件调查、探索陌生代码,
  或文件阅读量将超过 5k token 的调研
- **直接读取**:明确知道只需查看哪 1-2 个文件时
- 子代理不继承对话历史——在提示词中提供完整上下文

## 压缩指令

上下文被压缩时,请在摘要中保留以下内容:

- 对 `production/session-state/active.md` 的引用(读取它以恢复状态)
- 本次会话修改的文件清单及其用途
- 已做出的架构决策及其理由
- 当前 Sprint 任务及其状态
- 代理调用及其结果(成功/失败/受阻)
- 测试结果(通过/失败数量、具体失败项)
- 未解决的阻塞或等待用户输入的问题
- 当前任务及所处步骤
- 当前文档哪些小节已写入文件、哪些仍在进行中

**压缩之后:** 读取 `production/session-state/active.md` 以及正在处理的
文件,以恢复完整上下文。文件承载决策;对话历史是次要的。

## 会话崩溃后的恢复

如果会话中断(“prompt too long”)或你开启新会话继续工作:

1. `session-start.sh` 钩子会自动检测并预览 `active.md`
2. 读取完整状态文件获取上下文
3. 读取状态中列出的未完成文件
4. 从下一个未完成的小节或任务继续
